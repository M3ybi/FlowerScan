# Household billing history

This change is limited to the existing Billing & history section and the facts it reads. Current-plan cards, available plans, purchase/cancel controls, entitlements, household limits and navigation retain their existing behavior.

The section presents meaningful subscription and billing events newest first. All, Billing, Plan changes and Renewal filters operate on loaded history without requesting data on each chip click. Four matching events appear per page; the visible slice is then grouped by local month/year. Previous/next controls show the selected filter's page and event counts. Single-page and empty results omit pagination. Filter/household changes reset to page one, while same-household updates preserve the requested page and clamp it after the complete result arrives.

To obtain truthful normalized totals, the timeline completes the existing bounded 50-row reads before displaying cards or page counts. For 400 raw rows this requires eight sequential reads, while only four normalized cards are rendered at once. Loading keeps the current skeleton design; a failed remaining read stops collection and offers Retry for that cursor. Page/filter navigation after completion is local. The history query, normalization, deduplication and ingestion are unchanged.

On mobile, optional single-finger swipes on the card area move between pages. They require at least 64px of horizontal movement with clear horizontal dominance, ignore viewport-edge/control starts and cancel after dominant vertical movement. They never prevent native touch defaults or capture scrolling. Semantic 44px arrow buttons remain the primary interaction. The page area reserves its previously measured height, resets that measurement on filter/household/width changes, and has no inner vertical scrollbar. A 180ms opacity transition runs only when reduced motion is not requested. Page changes may align the history header if it is above the viewport; they never scroll the application to its top.

History is scoped to the authenticated account and selected household. Owner and active Viewer membership permits informational history access; history rows contain no billing management actions. Changing households immediately masks the old result and cancels its ability to update the displayed history. Provider customer IDs, transaction IDs, raw payloads and internal identifiers are never rendered.

Descriptions use event-time plan and period facts. A legacy row without a previous plan or billing period receives a generic accurate description. The current household plan is never used to reconstruct historical transitions. Cards are informational rather than clickable when there is no additional useful detail.

## Duplicate audit and historical accuracy

A read-only audit found four renewals on October 6, 2026, around 19:00, 19:05, 19:10 and 19:15 UTC. Their stored provider events have distinct successive five-minute billing periods. They are separate renewals and must remain separate in the timeline. The retained provider payload does not identify the environment, so the audit does not establish whether these were sandbox/test events. An observed switch to Free followed by a delayed renewal also represents separate recorded lifecycle observations.

Deduplication uses stable provider event identity and, where available, the same receipt and renewal period. It never collapses events merely because their title, plan or timestamps look similar. Internal sync/reconciliation noise is excluded from the presentation; real lifecycle transitions remain visible.

## Rollout and verification

Deploy the additive history migration before the frontend that selects its fields. Existing rows retain their stored plan and time, with unavailable historical facts left unknown. The migration adds event facts and informational read access; it does not rewrite purchase, cancellation, entitlement or membership decisions.

Behavioral tests cover normalization, ordering, grouping, categories, duplicates versus legitimate periods, historical plan text, sensitive-field exclusion and household request isolation. An isolated browser fixture uses the production timeline and stylesheet to check filters, mobile overflow and clearance above the existing bottom navigation. Its external data boundaries are mocked; it does not prove a real payment or provider delivery.

The original timeline rollout was validated on October 7, 2026: the full suite passed 450 tests, followed by the final 13 history UI and 15 model/query/controller tests after the last focused adjustments. Type checking, production build and Android debug assembly passed. The original browser fixture passed 22 DOM checks in each of 10 desktop/mobile scenes, including a true 390px CSS viewport and final-card clearance above the unchanged production navigation.

The navigation-only update passed the full 456-test suite and all 18 focused history UI tests. Final type checking, production build and Android debug assembly passed. The expanded StrictMode browser fixture passed 43 checks in each of eight desktop scenes and 44 checks in each of eight 390px mobile scenes, including first/middle/last pages, bottom-navigation clearance, loading, empty, error and reduced-motion preferences. It exercises the real history hook and normalization with substituted repository/auth boundaries, bounded collection of 400 events, failed-cursor Retry, stale-account/household responses, filter resets, page clamping and conservative gestures. Input and scrolling are programmatic; trusted physical keyboard/swipes, device safe areas, native edge navigation and live checkout are not exercised. Reduced-motion virtual-clock runs verify the committed height reservation and disabled animation because computed bounds can lag the DOM in that mode; normal-motion runs also assert measured height stability. This update requires no database migration.

The existing household billing fixture and the new history fixture passed together with the migration in a single rolled-back database transaction. The migration was then deployed, and a read-only check confirmed all eight fact columns, three deduplication indexes and the member read policy, with no missing event times or retained synthetic history users.
