## Security report

The completed Codex Security baseline scan is `73b2fcc6-d851-4875-8e74-4f96569de04f`, bound to immutable revision `2e8e933`. Its canonical report, findings, coverage, manifest, threat model and SARIF remain in the local Codex Security scan artifacts and were not rewritten after completion. The worktree changed during remediation; that drift is explicitly recorded by the scan.

Two medium, high-confidence findings were validated: **repeated household invitation delivery** (`csf_0286ae887991a72410932f6a`) and **paid diagnosis without independent request admission** (`csf_6c76a2cff868bbc9798924e4`). An authenticated eligible account and configured provider are prerequisites. Impact is provider cost/capacity, unsolicited repeated mail and sender reputation; a cross-household read/write bypass was not established.

Both paths now use the existing atomic per-user admission function before provider work. Diagnosis receives 30/hour, including Premium; invitation mail receives six/hour across households plus provider idempotency and a bounded request. These anti-abuse limits do not change monthly product entitlements. Endpoint tests and independent-session PostgreSQL contention pass. Safe failures keep provider internals out of client responses/logs. Provider-side aggregate spending/account creation abuse remains an operational boundary; per-user limits are not a global spending ceiling.

The baseline inventory had 405 tracked entries. **345 first-party source entries received substantive complete reads**, including CSS, translation/copy dictionaries, static catalog data, browser/test fixtures, SQL fixtures and deployment prose. Explicit remaining categories were 54 binary assets, three third-party license bodies, one lockfile reviewed as dependency metadata, and two empty `.gitkeep` files. Third-party implementation, external project/provider settings, original device file providers and physical devices are not covered by that semantic-source claim. Current changed boundaries additionally received independent frontend/backend/infrastructure reviews and narrow verification after fixes.

Deletion requests now persist under the authenticated JWT subject with self-only reads, no client status/audit writes, idempotent creation and private status audit. No automatic deletion or new public administrative authority is introduced. Operator assignment, retention, shared ownership, billing and final identity verification policy remain explicit operational decisions.

Signed sandbox/Test Store webhooks are ignored by default before privileged writes. Production/signed historical omitted-environment compatibility remains. Existing records are not retrospectively classified or revoked. This is containment of an external configuration uncertainty, not evidence that old records were fraudulently granted. Review/tester purchase routing requires a release decision before deployment.

Secrets remain server-side. Registry audits report zero vulnerabilities and the emitted-client scanner passes, with known-token/private-key/privileged-JWT scope. It cannot recognize every arbitrary secret value. No real credential was reported in reviewed tracked source; no secret values are included in these reports.

The derived security-hardening assessment prefers proportionate local remediation using the existing shared admission boundary. A durable invitation worker/outbox would add job/retry/deployment/retention responsibilities and is not justified by the current evidence alone. The separate managed hardening portfolio preserves that reasoning without changing the sealed scan or claiming unimplemented architecture.

Measured scan-linked usage returned by the tool: **67,311,963 total tokens; 67,184,516 input; 65,611,392 cached input; 127,447 output; 35,061 reasoning-output; four measured threads; complete usage coverage**. These are cumulative thread-linked measurements, not an isolated incremental audit bill.

## Implementation status and remaining work

Implemented and locally verified: receipt fallback; request deadline settlement; save-result handling; mounted purchase intent; diagnosis cleanup/schema checks; feature decomposition/lazy screens/error boundaries; shared modal focus/scroll handling; durable deletion queue; provider admission; sandbox guard; CI and disposable-database verification.

Implemented but not externally exercised: hosted reusable CI/deployment gating, production migrations/functions, live provider configuration and native store flows. The exact reported handset gallery failure remains unverified. Desktop image/workflow tests are strong regression evidence but do not establish the affected phone's root cause.

External gates: full Supabase stack/staging RLS/Storage tests; production OAuth/RevenueCat/Netlify configuration; an accountable deletion-review process and approved retention/ownership/subscription policy; actual Android/iOS camera/gallery/Files/cloud-provider and repeated-save tests; Xcode build/signing; real sandbox purchase/restore/refund and auth-email recovery tests. These require the relevant environment or production authorization.

Technical debt remains in App's shared lifecycle/hoisted form state and the broad repository adapter. The implementation preserves those dependencies explicitly rather than introducing a second global state object. Further decomposition should follow measured maintenance needs and targeted regressions. No claim is made that this audit found every possible defect or that all platform release gates have passed.
