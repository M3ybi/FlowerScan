# Consecutive image selection and shared picker

This records the earlier `c9718e3` implementation. The inline Camera/Gallery menu and FileReader-first provider handling were subsequently replaced; see [the current modal and provider-read report](plant-action-modals-2026-10-16.md).

## Findings and evidence

The reported sequence is one successful plant creation followed by a generic photo-processing failure on the next gallery selection. The original failing photo and affected Android browser session were unavailable, so the exact device/provider exception cannot be asserted as fact.

The precise client operation reproduced in a regression test was the original signature read, `file.slice(0, 12).arrayBuffer()`, in `preprocessImageFile`. It ran outside the processing error boundary. After a successful first image, a second File throwing `NotReadableError` escaped unchanged, and the App displayed its generic processing message. This test failed before the fix with numeric DOMException code `0` instead of a public image error code.

The original pipeline also read the provider-backed File again for bitmap decoding and potentially again through an object URL for HTML decoding. A gallery grant/read problem between those operations could invalidate an otherwise supported image. That device-specific mechanism is an inference; it was not observed on a physical handset. The revised pipeline reads the selected File into an owned Blob once, retries one transient `NotReadableError`/`InvalidStateError` with a fresh reader, and uses that snapshot for all decoding and compression attempts. Permanent read failures now identify the read stage and explain how to choose a locally available photo.

Additional confirmed lifecycle defects were found by inspection and controlled browser tests: modal closure did not invalidate pending captures; the household-only guard did not detect App unmount; native picker cancellation was treated as an error; and pending native OS pickers had no shared serialization across modal lifetimes. Old work could retain resources or finish into a later form session. The shared selection hook now owns the operation controller, preview URL, loading lock, current scope, and mounted state. An old completion cannot replace a newer image, clear its spinner, or update an unmounted component. Native OS pickers are serialized because AbortSignal cannot dismiss them.

## Implementation

- `ImageSourcePicker` is used by both Add Plant and Plant Diagnosis. Clicking Add Photo expands two choices, Camera and Gallery, using existing translated labels. On Capacitor, both call the existing Camera plugin through the capture service. On web, separate hidden file inputs provide `capture="environment"` for Camera and an ordinary gallery/file picker for Gallery. Browsers without direct capture support fall back to file selection. Selected inputs reset only after their asynchronous work settles; empty selections are ignored.
- `useImageSelection` shares processing, server safety validation, cancellation, retry, preview ownership and localized errors. Modal/component closure, navigation, household changes and unmount invalidate pending work. Failed replacements preserve the previous photo; clearing occurs after successful plant creation or household reset. The App also refuses submission while a synchronous image lock is active.
- FileReader instances are fresh per read and release event/abort listeners. Byte reads and output reads have explicit error handling. Bitmap and canvas resources are released; HTML decoder disposal also clears its image source. JPEG/PNG decoding requests an early bounded bitmap when dimensions and orientation are unambiguous. The canvas enforces the final bound for every format.
- Empty/generic MIME types from device providers are inferred from actual bytes. Recognized MIME/signature mismatches remain rejected. HEIC/HEIF brands are recognized and attempted only through available platform decoders; successful conversion must produce validated JPEG bytes. Unsupported decoding returns an unsupported-format error. No HEIC codec dependency or extension-based relabeling was added.
- The existing 15 MiB original / 2 MiB processed contract remains. Maximum output dimension is 1600 pixels with preserved aspect ratio and orientation; initial JPEG quality is 0.85 with five bounded attempts down to 0.65 and reduced dimensions. The preferred size is under 1 MiB; a valid first result between 1 and 2 MiB retains its quality. Decodable JPEGs already within the bounds and without EXIF/IPTC/comment metadata avoid another lossy encode.
- Read, decode, compression, format, upload, household access and camera permission errors are distinct. All public image errors are translated into English, Slovak, German, French and Spanish. Development logs contain only a controlled stage, whitelisted exception name and public code; no filenames, URLs, image bytes, tokens, account identifiers or raw provider messages are logged.
- Selection cancellation propagates to validation HTTP requests through the existing timeout helper. AbortController provides compatibility without requiring `AbortSignal.timeout`, `AbortSignal.any`, or `Blob.arrayBuffer` on supported browser paths.

## Storage and plant integrity

Selection performs safety validation but does not upload objects or create plants. The repository upload and atomic plant-creation RPC retain their authorization, mandatory server safety checks, private bucket paths, bounded retry identity, write-recovery checks and cleanup behavior. No account-specific permissions, database schema, bucket policy, provider configuration or AI diagnosis contract changed in this patch.

The existing distributed-write limitation remains: abrupt client termination or an ambiguous network failure can prevent confirmed cleanup of a potentially referenced upload. Existing recovery preserves uncertain committed images rather than deleting a valid plant's photo. The ordinary failed-save cleanup and retry behavior are covered by source-of-truth tests; this change does not claim an atomic transaction spanning Storage and PostgreSQL.

## Release and remaining limits

Release the web bundle through the normal main-branch deployment. Rebuild/release the Android application to deliver the new assets to native installs; no new server secret, Edge deployment or database migration is required. Existing deployed server image limits and safety validation remain compatible.

Not executed: physical Android/iOS camera and gallery, actual affected-user sessions, a real HEIC/HEIF decode on a supporting device, or low-memory process termination. Very high-resolution images with complex orientation metadata or HTML decoder fallback still depend on platform decoding memory; failure is reported without returning the original image as an unsafe fallback. The client cannot recover a photograph that the OS/provider never permits it to read. These limitations are distinct from the reproduced client error boundary and lifecycle defects fixed here.
